# МЕТАФЛОРА* нейро

Самодостаточный Telegram-бот-агрегатор. В проект входят каталог моделей, нативные Telegram-настройки, тарификация в метакоинах, профиль, реферальная программа, промокоды, маршрутизация провайдеров и постоянное хранилище.

## Что хранится в проекте

- каталог моделей, карточки, входные данные и доступные настройки;
- тарифы, пакеты метакоинов и правила перехода между тарифами;
- расчёт стоимости запуска с резервом на переключение провайдера;
- профиль, пользовательские настройки и выбранная модель;
- реферальные связи, начисления, бонусы и заявки на вывод;
- генератор и учёт промокодов;
- Docker-образ и Railway-конфигурация.

Экономика описана в [docs/metacoin-economics.md](docs/metacoin-economics.md), реферальная механика в [docs/referral-program.md](docs/referral-program.md), эксплуатация Railway в [docs/railway-operations.md](docs/railway-operations.md).

## Локальный запуск

1. Создай `.env.metaflora-neuro.local` рядом с каталогом проекта или передай переменные окружения.
2. Запусти `npm ci`.
3. Запусти `npm test`.
4. Запусти `npm start`.

Платные вызовы провайдеров выключены, пока `ENABLE_PAID_PROVIDER_CALLS` не установлен в `true`. Checkout можно подключить через YooKassa или отдельный T-Bank/SBP gateway. Без настроенного платёжного контура карточка счёта работает как безопасная заглушка и ничего не списывает.

## T-Bank/SBP checkout

Бот сохраняет локальный заказ, выпускает подписанный ticket на 15 минут и отправляет пользователя в `metaflora-payment-demo`. Gateway создаёт СБП-платёж и возвращает подписанный callback. Тариф или метакоины начисляются только для `CONFIRMED`, если сумма и локальный `orderId` совпали.

Для включения нужны `TBANK_CHECKOUT_ENABLED=true`, `PAYMENT_GATEWAY_URL`, `PAYMENT_CHECKOUT_SECRET` и `PAYMENT_CALLBACK_SECRET`. Те же секреты задаются в gateway; `BOT_TBANK_CALLBACK_URL` должен указывать на `https://<домен-бота>/internal/tbank/confirmed`. Checkout требует постоянный history backend.

## USDC/Base checkout

Криптовалютный rail отделён от RUB/SBP: суммы хранятся целыми `amount_usdc_micros`, сеть фиксирована как `base`, способ оплаты — `crypto_usdc`. Бот подписывает короткоживущую Coinbase-котировку с неизменяемыми товаром, суммой и начислением. Callback принимается только на `/internal/crypto-usdc/confirmed` с корректным HMAC, свежей временной меткой и подтверждённым событием Coinbase Business; повтор события безопасно обрабатывается по `eventId`.

Для включения нужны `CRYPTO_USDC_CHECKOUT_ENABLED=true`, безопасный `CRYPTO_USDC_GATEWAY_URL`, отдельные `CRYPTO_USDC_QUOTE_SECRET` и `CRYPTO_USDC_CALLBACK_SECRET` длиной не менее 32 байт и `CRYPTO_USDC_PRICES_JSON` с отдельной ценой каждого доступного товара в USDC micros. На gateway они должны совпадать соответственно с `CRYPTO_QUOTE_SECRET` и `PAYMENT_CRYPTO_CALLBACK_SECRET`, а `BOT_CRYPTO_CALLBACK_URL` должен указывать на `https://<домен-бота>/internal/crypto-usdc/confirmed`. Gateway принимает прямой перевод USDC в сети Base и независимо проверяет receipt; Coinbase/MoonPay не используются. Пока любой обязательный элемент bot/gateway-конфигурации отсутствует, rail остаётся выключенным и кнопка не показывается.

Каждая опубликованная строка `CRYPTO_USDC_PRICES_JSON` задаёт независимые `amountUsdcMicros` и `openrouterUsdcMicros`; доля владельца вычисляется как разница. Все суммы должны быть выровнены до цента, доля OpenRouter — не меньше `5250000` micros (минимальные $5 кредита и 5% комиссия), а доля владельца — неотрицательной. Для позиций дешевле $10.40 этот обязательный минимум осознанно уменьшает долю владельца; цена для пользователя не повышается. Невалидный SKU не запускается, батчинг не используется.

Подтверждение создаёт отдельную запись `crypto_usdc_finance_requests`, затем идемпотентно начисляет пакет или активирует новый тариф и только после этого переводит платёж в `fulfilled`. Происхождение entitlement фиксируется как `crypto_usdc/openrouter`. Ошибка начисления возвращает gateway ошибку для повтора; upgrades и renewals через crypto пока закрыты. Поток не пишет USDC в RUB-копейки или Stars, не создаёт `provider_topup_requests` и не запускает OpenRouter funding worker.

## Промокоды

Промокод создаётся в той же постоянной базе, которую использует бот:

```bash
npm run promo:generate -- \
  --code START100 \
  --type metacoins \
  --value 100 \
  --uses 500 \
  --expires 2026-12-31
```

Для скидки используй `--type discount_percent`. Параметр `--code` можно не передавать, тогда код будет создан автоматически. Один пользователь может активировать конкретный код только один раз.

В Railway команда выполняется внутри контейнера:

```bash
railway ssh npm run promo:generate -- \
  --type metacoins \
  --value 100 \
  --uses 500
```

## Данные

Рабочее состояние старых сценариев пока остаётся в SQLite на Railway. Полная история бота пишется в отдельный Supabase-проект: пользователи, диалоги, сообщения, генерации, метакоины, платежи, промокоды, входящие Telegram-апдейты и вызовы внешних API разнесены по разным таблицам схемы `neuro`. Исходные и готовые файлы лежат в закрытых Storage-бакетах, а PostgreSQL хранит их метаданные и связи.

Миграция находится в `supabase/migrations/202607270001_neuro_history.sql`. Для подключения нужны `SUPABASE_DATABASE_URL`, `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` именно от проекта бота. Без них журналирование отключается и не мешает основным сценариям.

В репозитории и Docker-образе нет API-ключей. Токен Telegram, ключи провайдеров и доступ к Supabase передаются только через переменные Railway.
